# Changelog

All notable changes to the GQODB open layer are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versions follow Cargo's 0.x
convention: a change that is not backwards-compatible bumps the minor version, and
0.x versions carry no stability promise (see [docs/API_STABILITY.md](docs/API_STABILITY.md)).

## [0.1.0] - 2026-10-18

First public preview, source only. Released on 2026-10-18 as a GitHub pre-release (tag `v0.1.0`,
unsigned); not published to crates.io (see [docs/RELEASING.md](docs/RELEASING.md)).

### Added

- Four crates: `gqodb-types` (exact event and time types), `gqodb-blocks` (lossless
  codec kernels, Parquet counter-tests, benchmark tooling), `gqodb-store` (indexed
  `.gqodb.ob` segments with range reads and committed-prefix recovery) and
  `gqodb-codec` (native format facade and file inspection).
- Two command-line tools: `gqodb-codec` (`inspect`, `validate`, `demo`) and `ob_store`
  (`inspect`, `verify`, `query`, `recover`), plus the `gqodb-blocks` benchmark binary.
- Native formats: `GQOREAL3`/`GQOADP02` tick blocks, `GQOREAL4`/`GQOBOOK1` order-book
  blocks and the `GQOBHDR1` indexed segment container. The header, not the file
  extension, selects the codec profile.
- Benchmark protocols, stored results with build receipts under `results/`, and
  `results/verify_public_evidence.py`, which checks the receipted result files against
  their receipts and recomputes the B11, B15 and B17 summaries (B06 in part; the B12 and B13
  figures are not recomputed).
- Source installer `install.sh` (asks before installing system packages or Rust) and
  `benchmarks/run.sh` (`verify`, `synthetic-smoke`; neither downloads market data).
- Crate metadata for all four crates (description, readme, keywords, categories,
  documentation, repository, licence, `rust-version`, versioned path dependencies).
  Packaging was checked with `cargo publish --workspace --dry-run` in a scratch copy;
  `publish = false` remains in the repository.
- `gqodb_blocks::real::MAX_DECODED_STRING_BYTES` (128 MiB), the limit above.
- Crate-level documentation and seven tested doc examples (`gqodb-types` 2,
  `gqodb-blocks` 2, `gqodb-store` 1, `gqodb-codec` 2). `cargo doc` builds without warnings.
- `docs/API_STABILITY.md`, `docs/RELEASE_NOTES_0.1.0.md`, `docs/RELEASING.md`.
- CI: minimum-supported-Rust job (1.85), doc-tests, rustdoc with warnings denied,
  `cargo deny` (licences, advisories, sources), a check that the per-crate licence files
  match the repository's, a check that `THIRD_PARTY_LICENSES.md` is current, and
  macOS and Windows build-and-test entries marked `continue-on-error` (first run on
  2026-10-18: macOS passed, Windows failed in one benchmark example test, see Known limitations). The third-party actions of the main CI workflow (`rust.yml`) are pinned by
  commit SHA; the nightly `fuzz.yml` is not pinned yet. Dependabot is configured weekly for
  Cargo and GitHub Actions.
- B17: a file-level trades benchmark on public Binance Vision data against Parquet, DuckDB and
  ClickHouse, with pre-registered protocol, addenda, per-sample results and build receipts. Run 2
  (`results/b17-public-trades-20261018/`) is the main result, measured on the released commit
  `c07fbde`; run 1 (`results/b17-public-trades-20261017/`, an earlier commit, before the limit on decoded
  string bytes) is kept for comparison. Against the strongest baseline per axis, GQODB
  stores 3% to 19% fewer bytes than DuckDB Parquet-zstd on the two day-slices, and writes and
  reads warm about 9-25% faster than the strongest Parquet configuration (V1; against ClickHouse the
  warm range-read point estimates run from 0.33 to 1.24 over the cells, one of them, S2/v1 against
  `clickhouse-default`, without a win); its write peak
  memory is 2.2 to 4.3 times that of the DuckDB Parquet writers (up to 5.0 on the full months;
  the adapter path loads the whole table first, for every Rust candidate). Two cells of run 2 are
  UNDERPOWERED (D2/v1 and D2/v2, 11 and 12 valid rounds). Every loss is in
  the README. The earlier headline "wins every axis (B06)" is withdrawn. B17 uses two months of
  public data (3.1 and 3.7 million rows, and two 1,048,576-row slices) and also reports reads
  after page-cache eviction, so the older "warm caches only, up to one million rows" bounds of
  B06 to B15 do not apply to it. The protocol was amended once during run 1 (addendum A-004).
- Fuzzing: a `cargo-fuzz` harness with 15 targets, `docs/FUZZING.md` and a nightly workflow
  (`.github/workflows/fuzz.yml`, not yet run on GitHub).
- `deny.toml`, `THIRD_PARTY_LICENSES.md` (generated by `scripts/third_party_licenses.py`),
  per-crate copies of `LICENSE` and `NOTICE`.

### Fixed

Nine defects: eight found by fuzzing the readers, one (fix 9, the unbounded string expansion) found by reading the code. Each has a regression test in
`crates/gqodb-blocks/prototype/tests/malformed.rs`. Fixes 2 to 6 and 8 have a stored reproducer
under `tests/regressions/`; fixes 1 and 7 have none (their tests build the input inline).
No file format or valid-input encoder output changed.

- `GQOREAL3` decode: integer underflow on a 12-15 byte block with a valid checksum.
- Parquet reads: panics from the `arrow-ipc`, `parquet` and `arrow-buffer` dependencies on
  forged input are contained and reported as decode errors (this needs unwinding panics).
- Parquet footer and page headers: unbounded skip loop (a CPU hang on a 0.8-2 KB input) is
  now guarded by a budgeted walk. Upstream issues have not been reported.
- Parquet encoder: duplicate column names that need different encodings now return an error
  instead of panicking.
- Unchecked decoding layer (`real::decode`, `Decoder::decode`, `batch::Options::decode`,
  `Reader::read_block`, `read_all`, `visit_blocks`, `query`, `profile_read_all`, `recover`, and the
  `ob_store verify|query|recover` commands): a crafted block of about 60 KB could request
  `rows x longest dictionary string` = 62,914,560,000 bytes for a string column and abort the
  process. Decoding now refuses a block whose decoded string bytes (dictionary entry length over
  the valid rows, summed over all string columns) exceed 128 MiB, before allocating them.
  `real::encode` applies the same limit, so a batch above it is now an error (also from
  `Writer::append` and `gqodb_codec::encode`); encoder output below the limit is byte-identical
  and no file layout changed. Regression tests in `crates/gqodb-blocks`, `gqodb-store` and
  `gqodb-codec`, and stored reproducers (`tests/regressions/string_bomb_60kb.bin`,
  `string_bomb_segment.gqodb.ob`).

### Known limitations

- No stability promise for APIs, command-line interfaces or file formats.
- Benchmark figures are observations from named runs on one host; B06 to B15 are warm-cache
  runs on up to about one million rows, B17 uses 3.1 to 3.7 million rows and also reports
  page-cache-evicted reads. See the README for what has not been measured (a cold device,
  datasets above about 3.7 million rows, other venues, multi-threaded use, other platforms).
- Adversarial fuzzing of the readers is partial (15 libFuzzer targets, at least 35 minutes each on one
  machine, not exhaustive); nine defects found (eight by fuzzing, one by reading the code), nine fixed, none open. The unchecked decoding
  layer (`real::decode`, `Reader::read_block`, `read_all`, `visit_blocks`, `query`, `recover`, and
  the `ob_store verify|query|recover` commands that call them) remains unaudited: the 128 MiB limit
  on decoded string bytes closes one class, not all (for example, the numeric columns of a block are
  not capped there). Use the checked entry points (`gqodb-codec`, `Reader::read_block_bounded`) for
  untrusted files. See [docs/FUZZING.md](docs/FUZZING.md).
- `real::encode` now refuses a batch whose decoded string bytes would exceed 128 MiB (see Fixed).
- Only Rust 1.85.0 and 1.96.0 were tested, on Linux. In the first GitHub CI run (2026-10-18) the Linux,
  MSRV, `cargo deny` and macOS jobs passed; the Windows job failed in the benchmark example test
  `fsync_tree_handles_files_and_directories` (opening a directory to fsync it gives `Access is denied`)
  and stops there, so Windows is not supported yet.
- Directory sync and physical power-loss behaviour of segment files are not qualified.
- Crates are not published to crates.io; `Cargo.toml` keeps `publish = false`.
- Some crate READMEs under `crates/` are partly in Dutch.
